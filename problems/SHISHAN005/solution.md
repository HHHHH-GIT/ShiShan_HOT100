# SHISHAN005 · 消息接收重复问题 官方题解

## 1. 题目背景与现象剖析

在大型即时通讯（IM）与分布式协作系统中，保证消息“不重、不漏、有序”是最核心也是最脆弱的一环。
工单中用户反馈的“消息重复”实际上并不是一个单一的 Bug，而是由于消息在生命周期的 **发送、消费、补偿、分页、重连合流** 5 个阶段中，分别存在独立的缺陷相互耦合而成的系统性问题。

每个缺陷单独在单元测试中运行都“看起来非常合理”：
- 发送接口在无并发时能返回成功并落库；
- 异步消费端正常接收并投递消息到收件箱；
- 补偿任务忠实地重发所有“尚未 ACK”的消息；
- 历史查询接口能查出历史消息；
- 时间线接口把历史和新消息组合输出。

但在真实高频交织的业务场景中，这些局部逻辑全部失效，导致了幽灵重复。

## 2. 五大缺陷根因与修复说明

### 缺陷 1：发送接口幂等边界竞态（Idempotency Race Condition）
- **现象**：客户端网络抖动快速重试发送时，历史库中落入了两条不同自增 `id` 但 `clientMsgId` 相同的重复消息。
- **根因**：`ChatService.sendMessage` 采用了“先查再插”的非原子操作（Check-Then-Act）。并发重试请求在同一毫秒穿透了 `findByClientMsgId` 为空的判断，导致各自生成了不同的递增 ID。
- **修复**：在内存映射中采用原子的 `computeIfAbsent` 或对 `clientMsgId` 加锁，保证同一客户端消息 ID 全局只产生并持久化一次。

### 缺陷 2：收件箱事件消费非幂等（Non-idempotent Event Consumption）
- **现象**：异步事件队列重试或重复投递时，用户实时收件箱直接追加了重复项。
- **根因**：`InboxRepository.add` 无论该消息是否已存在于该用户的收件箱列表中，都直接执行 `list.add(msg)`。
- **修复**：在将消息存入用户收件箱前，检查该消息的 `id` 是否已经存在，若已存在则忽略此次重复投递。

### 缺陷 3：未确认补偿扫描缺失在途时间窗口（Premature In-Flight Compensation）
- **现象**：正常发送消息后，客户端尚未发出 ACK（处于正常网络在途传输中），后台补偿任务立刻介入，导致收件箱再次收到一次重复推送。
- **根因**：`CompensationWorker` 的扫描条件仅仅是 `!message.isAcked()`，缺乏对“消息创建时间”的超时阈值判定。一条仅发出几毫秒的消息被误认为“丢失”并触发了补偿重发。
- **修复**：增加时间窗口阈值（例如仅对 `!message.isAcked() && (System.currentTimeMillis() - message.getCreatedAt() >= 3000)` 的消息执行补偿重发）。

### 缺陷 4：历史游标分页闭区间越界（Off-by-one Cursor Boundary）
- **现象**：客户端翻页拉取历史记录时，上一页的最旧一条消息在下一页的第一条再次出现。
- **根因**：过滤条件错误地写成了 `before == null || m.getId() <= before`。游标本身是上一页最后一条消息的 ID，下一页拉取的应当是严格比游标更早的消息。
- **修复**：将过滤条件改为严格小于：`before == null || m.getId() < before`。

### 缺陷 5：全量时间线合流缺少全局排重（Timeline Merge Lacks Deduplication）
- **现象**：客户端断线重连调用 `/api/chat/timeline` 时，消息条数翻倍，每一条消息都出现两次。
- **根因**：`TimelineService`（或 `ChatService.getTimeline`）将落库历史列表与实时收件箱列表简单执行了 `addAll` 拼接，而实时收件箱中的消息原本就是历史消息的一份镜像投影，直接拼接必然全部重复。
- **修复**：采用按消息唯一标识（`id`）为键的有序集合或 Map（如 `LinkedHashMap<Long, Message>`）对两个数据源进行合流去重，最后统一输出。

## 3. 架构对比总结

| 阶段 | 屎山版本（Starter） | 修复版本（Reference） |
| :--- | :--- | :--- |
| **发送落库** | 非原子先查后插，并发穿透生成多个 ID | 原子注册映射，确保客户端唯一标识对应单实体 |
| **事件投递** | 收件箱盲目追加 | 收件箱投递幂等去重 |
| **补偿任务** | 立即扫描未 ACK，在途消息被误判重推 | 增加时间窗口（≥3000ms），在途保护 |
| **游标分页** | `id <= before` 导致交界处元素重复 | `id < before` 严格开区间单调下潜 |
| **时间线合流** | 历史与收件箱无脑拼接（`total = 2 * N`） | 统一按 `msgId` 指纹去重输出 |
