# SHISHAN005 · 消息接收重复问题

## 情景

我们正在维护一套企业级实时协作与即时通讯（IM）后台服务。
服务负责支持端到端聊天消息的发送持久化、向客户端实时收件箱投递、断线重连全量时间线合流，以及离线历史记录的游标分页拉取。

各子链路平时均由独立模块支撑：发送接口做客户端流水号校验，收件箱负责接收事件推送，后台有定时任务对未确认消息做轮询补偿，拉取历史有递减游标，客户端重连则聚合本地与远端会话数据。

单看每个子模块的逻辑与隔离单测，一切都运转正常。

## 现象

近期服务上线灰度后，客服与前端联调群里陆续转交了多张奇怪的工单：

### 投诉一

> **工单 #6102** —— 「弱网卡顿点快了，同一句话硬生生变成两条」
>
> 拿着手机在电梯或地下车库发消息，界面转圈稍有延迟，我连续点了两次发送按钮。
> 结果界面上硬生生弹出了两条一模一样的消息，接收方看到的也是两条！
> 客户端抓包确认这两次重试请求携带的 `clientMsgId` 流水号明明是同一个。
>
> —— 业务测试 小林

### 投诉二

> **工单 #6118** —— 「往上滑翻历史记录，某句话总会重现两次」
>
> 打开一个聊天窗口往上翻历史聊天记录，第一页拉到底，继续往上滑加载更早消息时，
> 上一页最顶部那句话，在翻上来的第二页顶头又重复出现了一遍！翻好几次都是这样。
>
> —— 前端研发 志强

### 投诉三

> **工单 #6145** —— 「重连刷新一下，整屏消息全翻倍了」
>
> 手机熄屏十分钟再打开，或者网络断开重连，客户端拉取一次完整时间线同步。
> 结果一刷新，界面上所有消息全变成双份了！原本 5 条变成了 10 条！
> 重新杀掉 App 再进又正常。排查了前端没有任何重复追加逻辑，数据全是接口吐出来的。
>
> —— 移动端组长 老徐

多张工单来自不同端和不同使用阶段的反馈，各个独立模块单独自测都看不出破绽 —— 请**先在本地把它们各自复现出来**，顺着消息全生命周期的状态机深入排障。

## 服务运行教程

```bash
mvn spring-boot:run
```

启动后：

- 服务监听端口为 `18084`，心跳接口是 `GET /hello`。
- 运行日志写在 `logs/app.log`。

自检服务是否就绪：

```bash
curl http://127.0.0.1:18084/hello
# {"status":"ok"}
```

## 你的任务

定位并系统性修复导致消息在不同生命周期阶段重复出现的**根因**。

业务验收：

1. **发送唯一性**：相同 `clientMsgId` 的快速重试请求，服务端严禁重复落库与多次投递；
2. **游标分页单调性**：以游标分页拉取历史消息时，相邻页面交界处的数据严禁重叠；
3. **在途消息保护**：未超时的在途消息在正常确认流程下，严禁被后台补偿机制误判重推；
4. **时间线合流排重**：离线历史与实时推送数据合流时，必须全局按消息唯一指纹排重，严禁翻倍。

约束：

- 项目里现有的接口路径、请求体字段、响应结构都是既有契约，不要调整。
- **不要靠屏蔽症状来通过验收**（比如直接在接口层对所有查询做暴力截断、或者把补偿逻辑整体删空等）。修完之后，单链路、状态流转和高频交互都要保持正确与稳定。
