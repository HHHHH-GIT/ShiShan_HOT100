# SHISHAN005 · 消息接收重复问题

## 情景

公司内部的即时通讯（IM）系统。同事们每天用它聊业务、建群拉通项目，前端网页端和手机 App 都在用。

最近团队重构了消息同步链路，刚灰度上线没两天，各业务群里就炸锅了 —— 大量同事反馈聊天界面里总能看到重复的消息，体验极差。前端同学被产品经理通报批评，熬夜抓包排查后自证清白：接口返回几条前端就渲染几条，前端完全按契约展示，重复数据全部来自后端。

## 现象

> **工单 #7021** —— 「聊天消息频繁异常重复，像自带回声」
>
> 灰度上线后，多个群里频繁出现消息重复展示：
> 有时发一条消息，屏幕上直接冒出来两条一模一样的气泡；
> 有时在群里往上翻看之前的历史记录，翻着翻着某句话又冒出来一次；
> 甚至手机放一会儿再打开或者重连，整屏聊天记录都会莫名其妙全变双份。
> 我们在低峰期单独发几条测试消息看着都挺正常，但只要放到真实交互场景里，各种重复现象就层出不穷。
>
> —— 前端研发 志强

## 怎么运行

在工程目录执行：

```bash
mvn spring-boot:run
```

- 服务地址：`http://127.0.0.1:18084`；心跳为 `GET /hello`，正常返回 `{"status":"ok"}`。
- 日志位置：`logs/app.log`，路径相对工程运行目录。
- 核心业务接口需要鉴权请求头（`Authorization: Bearer <token>`），可通过注册登录换取或携带预置测试凭证。

## 边界与验收

- 保持既有接口路径、字段、鉴权与响应格式，未登录或携带非法凭证时仍应返回 HTTP 401。
- 彻底消除消息在全生命周期各阶段的异常重复，服务端返回的消息流必须全局唯一且数据一致。
- 客户端消息标识区分大小写；同一标识在历史保留期间再次发送应返回原消息，不得重复落库或在收件箱中追加。不同标识即使正文相同，也各自保留。
- 消息撤回后展示为“[消息已撤回]”，重复撤回不增加气泡；历史分页游标 `before` 严格单调下潜，相邻页面无重叠消息。
- 客户端断线重连合并时间线时，必须全局去重；高频并发交互下服务吞吐与状态必须保持稳定。
- 严禁通过硬编码过滤、屏蔽异常或屏蔽测试用例来规避问题。
