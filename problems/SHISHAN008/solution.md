# SHISHAN008 · 张冠李戴

难度为 Candidate Master。它由一个原有身份缓存缺陷及三个出题时添加的耦合缺陷构成，围绕同一故障：报告与提交请求不一致。难度尚未经过模型通过率标定。

## 来源与外部边界

来源是本地 `F:\Projects\leetcode_analyzer`，其项目元数据声明 MIT。改造前直接调用 `fetch_code_samples`，用虚构身份和本地 GraphQL 响应验证：Alice 先分析自己后，Bob 分析 Alice 会得到私人代码且没有上游调用；反向顺序会让 Alice 本人被跳过。原项目 23 个已有测试均通过。

本题不保留真实力扣采集、JWT 兜底、缺字段降级、AI 调用或网络重试。`samples/upstream.json` 是完整固定记录；本地上游正确处理身份、权限及每页两条的完整分页。原有均匀采样器和启发式代码分析器原样保留，数据模型改为标准库 dataclass。分析器指标是现有近似口径，不要求把它升级为编译器。本题只验收行数、语言分布和样本数。

## 四类缺陷

1. **身份结果按报告对象存储。** `identity.py` 把描述当前 credential 的 `user_status` 放到 `profile:<target>` 下。修正为 `identity:<credential>`。公开资料、登录身份和私人提交有不同的作用域，不能用同一个“用户名”代替全部身份。
2. **前置索引忽略命名空间。** `cache.py` 的磁盘键由 namespace 和 key 共同生成，但进程内只用 key。只修复第一项，冷读可能正确，连续查询仍错误；只修复这一项，重新载入后的身份复用仍错误。参考实现使两层地址都包含 `(namespace, key)`。
3. **摘要投影共享嵌套数据。** `views.py` 只复制外层字典，删除嵌套 `content.code` 时改写了采样结果。它不改磁盘，所以 reload 会掩盖这个问题。参考实现对展示结果深复制；也可以使用不可变数据或逐字段构建全新的展示对象。只在最终序列化时补副本已经太晚。
4. **排队任务保存活动会话对象。** `jobs.py` 直接保存 session 引用，登录操作原地更新它。回执里的 viewer 保持不变，真正执行时使用的 account 和 credential 却变了。参考实现提交时深复制会话；也可以保存独立不可变的凭据快照。不能改用执行时身份，因为这违反任务契约。

starter/reference 的业务差异只有上述四处表达式。每项都能独立被验收发现；并不要求采用参考实现的具体数据结构。

## 验收设计

HTTP/workflow 用例从独立样本真值生成，直接按提交时的身份选择该用户记录，独立计算语言分布与非空行数；不读取服务运行结果作为预期。正文、摘要、公开资料、权限、任务回执、历史快照与重复执行均检查。摘要和受限报告显式禁止 `code` 字段。

`scripts/shishan008-cases.cjs` 维护样本和规格，`scripts/validate-shishan008.ts` 运行真实平台判题、三轮 starter 稳定性、四类单独回退、离线数据源契约、额外操作组合及解压启动。日志点使用由业务状态派生的 `REPORT_CONTEXT_DRIFT`，删除日志不能改变行为断言。

队列提供显式提交/执行接口是正常离线批处理工作流，用于确定性重放操作顺序；没有靠 sleep 或随机并发制造窗口。下载包不包含参考实现、隐藏用例或本题题解。

重复请求与语言范围缩小还验证上游资料读取预算；允许重新验证身份，但不能通过删除所有复用逻辑来回避隔离和对象归属问题。计数直接来自本地数据源的调用记录，不依赖日志或机器性能。
