# SHISHAN001 · 请求缓慢问题 — 解题说明

> 先自己动手。这份说明是给你定位到卡住时看的，不是让你照着抄的。

## 一、现象复盘

单人调用正常而混合请求频繁失败，只能说明需要检查交错执行的路径，不能仅凭症状就断言死锁。题目没有提供 CPU 利用率或重启实验结果，也不应把这些当作已知事实。

代码中的两次限时获取资源，加上日志中的等待位置，才是定位依据。每次 tryLock 最多等待 1000ms；一次请求还包含其他步骤，因此总耗时不必恰好为 1 秒。这是会由超时退出打破的循环等待，不是永久挂死。

> 为什么是「大面积」而不是「偶尔一两个」？因为一旦有一对线程咬住，它们会各自持有锁干等 1 秒；后面所有请求全排在这两个慢请求后面，于是连锁超时。

## 二、定位手段

### 1. 看日志

`logs/app.log` 里已经有关键线索。搜索 `TIMEOUT_GUARD` 和 `lock acquire timeout`，你会看到降级发生的确切位置和它等的是哪把锁。

### 2. 抓线程栈（最有效）

服务跑起来、压测正在冒 601 的时候，另开一个终端：

```bash
jps -l                       # 找到这个服务的 pid
jstack <pid> > stack.txt
```

在 `stack.txt` 里搜索 `BLOCKED` 或 `parking to wait for`。典型特征是这样一对线程：

```
"http-nio-18080-exec-12" ... waiting to lock <0x00000007...a0> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
                          ... locked <0x00000007...b8> ...   <-- 手里握着一把，等另一把
"http-nio-18080-exec-13" ... waiting to lock <0x00000007...b8> ...
                          ... locked <0x00000007...a0> ...   <-- 反过来了
```

**两个线程各握一把、互等对方那把** —— 这就是死锁的形状。多抓几次，看这两个地址对是不是固定的。

### 3. 读代码

带着 `jstack` 的结论回去看 `OrderService`，把**每一条写路径**上「获取锁的顺序」列出来。你会发现的不是「有没有加锁」，而是「加锁顺序不一致」。

## 三、根因

服务用两把全局锁分别保护库存和订单：`productLock` 与 `orderLock`。

- 下单路径：先拿 `productLock`，再拿 `orderLock`
- 取消路径：先拿 `orderLock`，再拿 `productLock`

这是教科书上的 **AB-BA 锁顺序反转**：

```
线程 A（下单）           线程 B（取消）
持有 productLock         持有 orderLock
  等待 orderLock   ←→      等待 productLock
        ↑ 互等，谁也走不了 ↑
```

单人操作时，两条路径不会同时在飞，永远撞不上。并发一上来，两个方向互相咬住，就形成了死锁。

服务并没有真的一直挂死，是因为加锁时设了等待上限（`tryLock` 带超时）：等满上限还拿不到，就放弃并抛异常，被全局异常处理器兜住，返回 `504` + `code=601`。**这个降级机制不是 bug，它是掩盖 bug 的那层纱布。** 你看到的是「系统繁忙」，实际是「两个线程在对峙」。

> **为什么第一次压测就能稳定复现？**
> 关键在于两条路径在拿到第一把锁之后、去拿第二把锁之前，都调用了 `WarehouseClient`（一次「跟仓储系统同步」的下游调用）。这个调用必须在临界区内完成 —— 否则会出现库存和仓储不一致。
> 于是「持有第一把锁」的时间被拉长到了亚毫秒级，两个方向撞上的概率从几乎为零变成必然。真实系统里这就是最常见的成因：**锁的粒度太大，临界区里夹了一次外部调用**。
> 这也意味着：光把下游调用挪出临界区，只是把撞上的概率重新压低，锁顺序反转依然存在 —— 那是把 bug 藏起来，不是修好它。

## 四、修复方向

核心只有一句话：**消灭锁顺序反转** —— 让所有涉及这两把锁的代码路径，都按同一个顺序获取。

具体怎么做，你自己选：

1. **统一加锁顺序**（最小改动）：把取消路径也调整为先拿 `productLock`、再拿 `orderLock`，和下单路径保持一致。
2. **收敛锁粒度**：既然库存和订单本来就属于同一笔业务操作，考虑用一把锁保护整个临界区，或者干脆按 `productId` 做分段锁，降低全局争用。
3. **改造数据结构**：库存用 `AtomicInteger` / `LongAdder`，订单表用 `ConcurrentHashMap` 的原子操作，把「需要复合操作的临界区」压缩到最小。

修完请自检：

- 并发压测跑满，**一次 601 都不能有**；
- `logs/app.log` 里不再出现 `TIMEOUT_GUARD` / `lock acquire timeout`；
- 取消订单的**幂等性**不能破坏（重复取消不能重复回补库存）。

## 五、判分会看什么

判题脚本会按顺序跑这几项，全部通过才算 AC：

| 测试点 | 类型 | 在验什么 |
| --- | --- | --- |
| 心跳探活 | 单请求 | 服务是否已经在 18080 端口就绪 |
| 单次下单 | 单请求 | 正常路径没有被你改坏 |
| 取消订单并回补库存 | 多步流程 | 取消的幂等性 + 库存精确回补（不能多补、不能少补） |
| 并发混合下单与取消 | 并发压测 | 50 并发 × 5 轮，**成功率必须 100%，不允许出现 504 / 601** |
| 日志中无死锁与超时降级痕迹 | 日志断言 | 本次运行期间没有再触发过超时保护 |

> 提示：并发压测那一项才是这道题真正的判分点。前两项是「别改坏」，最后一项是「对症」。
