# SHISHAN002 · 共享钱包的两副面孔 — 解题说明

> 先自己动手。这份说明是给你卡住时看的，不是照着抄的。

## 一、现象复盘

两条投诉看着都像「钱不对」，但它们的**证据形状完全不一样**，这一点至关重要：

| | 投诉一：深林余额小 1000 倍 | 投诉二：充值后刷新还是原值 |
| --- | --- | --- |
| 出现条件 | **必然**，每次查都错 | 充完值之后才出现 |
| 错的幅度 | 恒定 1000 倍 | 只差「刚充的那一笔」 |
| 数据库里的值 | **完全正确** | **完全正确**（财务对过账） |
| 星轨侧 | 正常 | 响应里承诺的 `balanceAfter` 也是对的 |
| 重启服务 | 没影响 | **恢复正常** |

注意最后两行：

- 投诉一的数据库是对的、星轨也是对的，**只有深林读出来不对** → 问题在「读」这条路上，而且只影响深林。
- 投诉二里「写」是对的（库对、响应也对），**只有「写完之后再读」不对**，而且**重启就好** → 这是一个**会被重启清掉**的东西，也就是内存里的缓存。

两条线索指向两个不同的根因，所以：

> **不要试图用一个改动同时解释两条投诉。** 分开定位、分开验证。

## 二、定位手段

### 1. 读日志

`logs/app.log` 里已经留了两条线索：

```bash
grep STALE_CACHE logs/app.log
grep "gameB read balance" logs/app.log
```

第一条会在「充值前后」出现，第二条会把深林读到的**原始值**、**换算后的值**和**最终返回的值**并排打出来 —— 三个数一看就知道谁多除了一次。

### 2. 用对账接口把两种单位并排看

```bash
curl http://127.0.0.1:18081/api/gameA/ledger/P001
```

响应里同时有 `unit` / `rawUnit` / `balance` / `balanceRaw`：

```jsonc
{"balance":1000.000, "unit":"CNY", "balanceRaw":1000000, "rawUnit":"厘"}
```

`balanceRaw` 和 `balance` 之间正好是 1000 倍。再回头看深林返回的 `1.000` —— 它是不是**在已经换好的数上又除了一次**？

### 3. 手动复现投诉二

```bash
curl http://127.0.0.1:18081/api/gameA/balance/P001          # 1000.000
curl -X POST http://127.0.0.1:18081/api/gameA/recharge \
     -H "Content-Type: application/json" \
     -d '{"playerId":"P001","amount":250}'                   # 承诺 balanceAfter=1250.000
curl http://127.0.0.1:18081/api/gameA/balance/P001          # 还是 1000.000  ← 问题在这
```

然后**重启服务**再查一次 —— 变成 1250.000 了。这一步能把嫌疑范围直接锁到「进程内缓存」。

### 4. 读代码

带着上面两条结论回去看：

- `web/GameBController.java` 与 `web/GameAController.java`：同一份数据，两边各做了什么处理？
- `service/WalletService.java`：`getBalance` 返回的到底是元还是厘？方法签名和注释有没有告诉你？
- `service/WalletService.java` 的充值方法：`cache.evict(...)`、`riskClient.preCheck(...)`、`ledgerRepository.credit(...)` 这三行的**先后顺序**是什么？

## 三、根因一：单位约定没有显式声明，深林侧重复换算

账本列历史存的是**厘**（1 元 = 1000 厘），对外接口一律是**元**。所以中间必然有一次换算：

```
对外（元） ──×1000──▶ 账本（厘） ──÷1000──▶ 对外（元）
```

换算被放在共享的 `WalletService` 里：

- `credit(playerId, 元)` 内部 **×1000** 写入账本
- `getBalance(playerId)` 内部 **÷1000** 后返回

问题在于：`getBalance` 的签名是 `BigDecimal getBalance(String playerId)` —— **返回值的单位既没写进方法名，也没写进注释**。于是「它返回的是元还是厘」只能靠口口相传。

- **星轨**：读写都走 `WalletService`，写的时候 ×1000、读的时候 ÷1000，**两处错误互相抵消**，看起来完全正常。
- **深林**：新团队从「账本存的是厘」这条旧约定出发，自己又除了一次 1000：

  ```java
  walletService.getBalance(playerId).divide(THOUSAND)   // getBalance 已经是元了
  ```

  于是深林拿到的是 **元 ÷ 1000**，正好比星轨小 1000 倍。

这就是「组合 API 没问题、单看就有问题」的本质：**星轨同时读写，两次换算互相抵消；深林只有读，没有任何东西替它抵消。**

## 四、根因二：先删缓存、再写库（Cache-Aside 时序错误）

钱包读操作走 Cache-Aside：**未命中就回源查库，然后回填缓存**。充值路径在屎山版里的顺序是：

```
1. cache.evict(key)                       ← 先把缓存删掉
2. riskClient.preCheck(playerId, amount)  ← 风控前置校验
   └─ 风控规则需要「当前余额」，于是调用 getBalance()
      └─ 缓存已空 → 回源查库 → 【把「充值前」的旧余额回填进缓存】   ★
3. ledgerRepository.credit(...)           ← 到这里才真正写库
```

★ 这一步是关键：**写库之前的那次风控读，把旧余额重新塞回了缓存**，而之后再没有任何失效动作。
于是缓存里长期躺着「充值前」的值（TTL 5 分钟），谁都读不到新余额。

外部表现就对上了：

- 充值响应里的 `balanceAfter` 是**服务端算出来的**（`balanceBefore + amount`），所以「显示已到账」没撒谎；
- 之后每次刷新都命中那份旧缓存，所以「无论如何刷新还是原值」；
- **重启服务清空内存缓存** → 重新回源 → 恢复正常。

> 注意风控那次读**不是可有可无的**：单笔充值不得超过当前余额的 10 倍是合规要求，它必须发生在写库之前。这就是为什么这个 bug 会**必然**复现，而不是偶尔才撞上。

## 五、修复方向

### 根因一（单位）

核心是**让单位在契约上显式化**，并且让两个游戏走**同一个**换算入口。可选做法：

1. 把方法名/类型改到「不会猜错」：`getBalanceYuan(...)`，或干脆返回一个 `Money` / `Balance` 值对象，把单位钉在类型上。
2. 深林侧改为复用共享入口（不要再自己动手换算）。
3. 顺手把 `UnitConverter` 收敛成唯一的换算出口，禁止别处再出现 `divide(THOUSAND)` 这种裸换算。

**错误做法**：在深林侧补一个 `× 1000`。那只是把错误又抵消回去，单位约定依旧是一团浆糊 —— 下一个人接进来还是会踩。

### 根因二（缓存）

Cache-Aside 的正确顺序是 **先写库（提交），再让缓存失效**：

```
1. 风控前置校验（读一次余额，回填与否都无害）
2. 写库并提交
3. cache.evict(key)      ← 提交之后再删
```

改完之后，无论第 1 步有没有回填、回填的是不是旧值，第 3 步都会把它清掉，下一次读必然回源到新值。

进阶层面的方案（本题不强制）：延迟双删、给缓存值带版本号/更新时间戳做读时校验、或者让缓存失效走消息总线保证最终一致。

### 修完请自检

- 同一玩家，星轨与深林的读数**完全一致**；
- 充值成功后立刻读，读到的是**充值后的余额**；
- 对账接口里 `balance`（元）、`balanceRaw`（厘）、最新流水三处自洽；
- 冷启动和跑热了都对；没有引入死锁或 5xx。

## 六、判分会看什么

| 测试点 | 类型 | 在验什么 |
| --- | --- | --- |
| 心跳探活 | 单请求 | 服务是否已在 18081 就绪 |
| 充值后立刻可读 | 多步流程 | **根因二判别点**：充值承诺的 `balanceAfter` 与随后读到的余额必须相等 |
| 单次交易结算 | 单请求 | 正常路径没有被改坏 |
| 两个游戏读到同一个余额 | 多步流程 | **根因一判别点**：星轨与深林对同一玩家的读数必须相等 |
| 入库单位与出库单位一致 | 多步流程 | 对账接口的对外余额、底层原始余额、最新流水必须完全自洽 |
| 并发混合读写 | 并发压测 | 50 并发混合读写全部成功，不出现 4xx / 5xx |
| 日志中无脏缓存回填痕迹 | 日志断言 | 本次运行没有发生过「写库前回填旧值」 |

> 注意「单次交易结算」和「入库单位与出库单位一致」在屎山版上**本来就是通过的** —— 因为星轨侧是自洽的。真正的判分点是那两个多步流程。

## 七、一个容易踩的坑

把风控那次读改成「绕开缓存、直连数据库」，确实能让测试通过 —— 但那是把**窗口压小**，不是把时序问题**修掉**：`先失效再写库` 这个顺序依然是错的，只要窗口里还有其他读（并发请求、别的业务分支），脏数据照样会被回填进去。

这跟「把死锁的下游调用挪出临界区」是同一类解法 —— 症状消失了，根因还在。正确的修法是**调整顺序**，或者引入版本号让脏值在读取时被识别出来。
