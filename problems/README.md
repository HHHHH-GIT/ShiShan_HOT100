# 出题手册

给这个题库加新题时，照这份规则来。**核心原则：题面是工单，不是教案。**

解题本质上是一次假设空间的搜索。题面每多给一句"解读"，就把假设空间压小一圈 ——
最坏的情况是解题者不读代码就能写出补丁，那这道题就废了。

## 一、题面的信息预算（`starter/README.md`）

**只允许出现这四类信息**，多一句都不行：

| 允许 | 说明 |
| --- | --- |
| 情景 | 系统是干什么的、有哪几个角色/调用方。**不写架构图、不写文件清单** |
| 现象 | 用户原话（工单体）、原始返回样例、复现命令。**不写任何解读** |
| 怎么跑 | 启动命令、端口、心跳、日志位置、种子数据 |
| 边界与验收 | 什么不能改、业务口径的成功条件 |

**禁止出现**：

- ❌ 代码结构树 / 文件名清单（解题者有 Glob / Grep，自己会看）
- ❌ 症状的差分诊断："两边差了整整一千倍"、"重启就好"、"数据库是对的"、"CPU 不忙所以是在等"
- ❌ 根因关键词（见下面的词表）
- ❌ 验收口径的逐条翻译（把 `tests.yaml` 里的断言改写成中文列一遍）
- ❌ 反向提示："不要直接把 XX 的降级逻辑删掉" —— 这等于告诉解题者 XX 存在且删了有效
- ❌ `meta.json` 的 `tags` / `summary` / `apiContract` 里同样不许出现根因关键词（它们也会展示在页面上）

**可移除性检查**：凡是你从题面删掉的线索，必须能在**代码注释**里找到（历史约定、业务约束、字段单位）。
删了代码里也没有的线索 = 把题变成猜谜，同样不合格。

## 二、分级提示（`hints.md`）

必须恰好三级，用 `## L1` / `## L2` / `## L3` 分节：

| 级别 | 只允许给什么 | 例子 |
| --- | --- | --- |
| L1 | 症状分类（"这两条投诉是两回事"） | 不含任何技术方向 |
| L2 | 提问式方向（"谁算出来的？"、"倍数是多少？"） | 不含答案 |
| L3 | 具体手法（抓栈、搜日志关键字、调日志级别） | 可以给关键字 |

`hints.md` **不进题目 zip**，只在网页端逐级解锁；判题结果会标注用到了第几级。
L1 里出现根因关键词视为不合格。

## 三、标签与用例命名

### 题目标签

`meta.json` 的 `tags` 一般由 **1–2 个编程语言 + 2–3 个技术标签**组成，语言排在前面。技术标签优先描述题目涉及的技术概念、协议或模型；主题单一时可以只有一个技术标签，不为凑数量添加标签。

- 语言使用标准名称，如 `Java`、`JavaScript`。不默认添加 `Spring Boot`、`Node.js` 等框架或运行时标签，也不使用“AI 助手”“游戏接入”等产品定位替代技术概念。
- 优先复用已有标签：`多线程`、`线程同步`、`数据一致性`、`读写时序`、`文件处理`、`哈希`、`生产者消费者模型`、`流式传输`、`SSE`、`缓存`。只有现有标签无法表达实际技术概念时才新增。
- 相同概念保持同名：文件上传与下载统一用 `文件处理`，涉及多线程的题目复用 `多线程`；允许不同题目使用完全相同的标签组合。
- 标签描述题目涉及的领域，不直接给出具体根因或修复方法。增加题目或调整标签时，同步更新中英文 README 的题目表。

### 测试点名称

`tests.yaml` 里每条用例要写两个名字：

- `name`：该测试点通过后展示，**可以带根因**，用于复盘。
- `displayName`：保留的中性名称，**必须中性**。未通过的点只展示序号、类型和状态；页面、API、SSE 采用同一规则。
- `description`：该测试点通过后显示，可写清验证目的。判题页按所查看运行的通过状态解锁并回放日志，详情页按最近一次判题的通过记录展示；历史 AC 不会解锁本次失败点。

判断标准：把 `displayName` 单独贴给一个没做过这道题的人，他不应该能推断出根因。

## 四、Issue 设计

- **starter 必须能跑，且单请求/正常路径全部正常** —— 缺陷只在特定路径暴露。
- **starter 与 reference 的 diff 越小越好**（单行级最优）：对照的价值就在于"改对了长什么样"。
- **缺陷必须确定性复现**。靠"并发碰运气"的题不要出 —— 判题会不稳定。
  需要放大窗口时，用一个**业务必需、删不掉的步骤**去放大（例如锁内必须做的下游同步），
  而不是往代码里塞 `sleep`。
- **不要用 `Thread.sleep` / `parkNanos` 做延迟模拟**：Windows 时钟粒度会放大到 ~15ms，
  破坏时延预算。用微秒级 `Thread.onSpinWait()` 自旋，跨平台一致。
- **给解题者留一条可检索的线索日志**（WARN/ERROR 级，带一个独有标记，如 `TIMEOUT_GUARD` / `STALE_CACHE`），
  `log` 测试点断言的也是它。这条线索和"删掉它就能过"必须解耦 —— 让它由业务路径派生。

### 关于"凑对输出"式解法

黑盒判题**无法从原理上**禁止解题者用"补一个反向系数"把错误抵消掉 —— 你只看到输出，看不到内部约定。
能做的现实手段：

1. **让同一个错误在多个独立出口各写一遍**（屎山里"同一个 bug 抄了三份"是常态）。
   补一处不够，成本就和"真正改对"相当了。
2. 在 `solution.md` 里明确点出抵消式解法为什么是错的（教育价值）。
3. 不要为了堵它而写"依赖内部实现"的断言（例如断言账本列的精度）—— 那会误杀合法的重构。

规则：**断言只能基于对外契约**。你可以要求"两个出口给出同样的结果"，不能要求"内部用某种单位存"。

## 五、发布前自查

文件下载的二进制完整性必须使用 `expect.bodySha256` 校验原始响应字节的 SHA-256（64 位十六进制字符串），不能只检查 `PNG` 等文本片段。`contains` 仍适用于文本内容检查。

平台改动可运行 `npm test` 执行隔离工作区中的回归测试，覆盖工作区重置、AC 状态、API/SSE 信息隐藏及二进制断言。

```bash
npx tsx scripts/lint-problem.ts --problem <ID>     # 泄题词 + 结构检查，必须零 error
npm run pack:problem -- --problem <ID>             # 打包
# 起 reference → 期望 AC；起 starter → 期望 FAIL，且失败点落在预期的用例上
# starter 连跑 3 次，失败集合必须完全一致
```

`lint-problem.ts` 会扫题面/提示/用例名/元数据里的根因关键词。词表在脚本顶部，按需扩充。
