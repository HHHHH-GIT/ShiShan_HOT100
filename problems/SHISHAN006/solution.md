# SHISHAN006 题解：事件完整，不等于连接结束

## 来源与问题边界

本题改编自 `HHHHH-GIT/SQL-Final-Project` 的 Node.js 会话服务。原工程的 `src/utils/llm.js` 使用逐行 JSON 解析、固定 `data: ` 前缀及 LF 分行；`src/routes/chat.js` 在上游迭代结束后直接保存并发送 `done`。这些均为实际存在的实现问题。

题目把模型替换为本地回放、MySQL 替换为内存存储，移除认证和非流式入口。没有引入随机竞争或延时。原工程的参数默认值、非流式变量作用域等其他问题不属于本题。

## 为什么普通请求没有问题

常规上游恰好每个事件只有一条 `data: ` 行，使用 LF，且发送 `[DONE]`。原实现可正确处理这种输入。已有 `TextDecoder.decode(value, { stream: true })` 和未完成行缓冲，所以简单跨包、中文字符拆到不同读取块不是本题根因。R002 与 R005 用逐字节读取覆盖这些回归边界。

## 四类问题

1. **字段语法被收窄。** `data:` 后的单个空格是可选的；`startsWith('data: ')` 会把没有空格的有效字段整体跳过。不能用全局替换空格修复，因为字段值和 JSON 字符串中的空白有自己的含义。
2. **行被当成事件。** SSE 以空行分隔事件，一个事件的多个 `data` 值应以 LF 拼接之后再解析。逐行解析会把合法 JSON 的不同部分分别送入 `JSON.parse`，随后被空 catch 静默丢弃。反过来，尚未收到空行的 `[DONE]` 也不能立即提交。
3. **行结束格式不完整。** SSE 允许 CR、LF、CRLF。必须跨读取块保留 CRLF 的关联；将所有 CR 简单删除会把 CR-only 事件粘起来。reference 遇到 CR 结束当前行，并跳过紧随其后的可选 LF。
4. **传输结束与业务成功混淆。** 正常 EOF 只代表没有更多字节，不能证明生成成功。`[DONE]` 必须作为完整事件到达，且之前没有解析或读取错误。错误事件后继续发 `done` 会让前端重新显示成功，因此解析器和保存流程都需要遵守完成约定。

## 修复实现

`src/llm.js` 按字节解码、行、事件三个层次处理输入：字段只去掉冒号后的一个可选空格；忽略注释和未知字段；在空行处拼接 data 并读取 JSON。本地协议允许空 data 作为心跳。损坏 JSON 或读取异常产生错误；没有完整完成凭据的 EOF 也产生错误。未结束事件被丢弃，不能补进正文。收到完成凭据后停止消费后续记录并释放 reader。

`src/completion.js` 只在收到凭据且没有错误时保存 `completed` 并发送 `done`。其余情况保存 `failed`，仅在上游尚未发送错误时补发一次错误事件。服务一直保留已经收到的有效正文与思考内容，不把错误提示覆盖进正文。

starter/reference 的业务源码差异仅在这两个文件；本地回放与界面在两边完全相同。`REPLY_EVENT_REJECTED` 来源于无效事件，`REPLY_RECEIPT_MISSING` 来源于完成检查。日志仅是诊断证据，删日志不会修复输出和状态。
