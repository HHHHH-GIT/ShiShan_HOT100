# SHISHAN003 · 失真的文件仓库：题解

## 先固定证据

分别保留上传请求、上传返回的指纹、元信息查询结果、下载内容。一个阶段失败可能挡住后续缺陷；查询恢复后仍要校验下载字节，不能只看到 HTTP 200 就结束。

## 指纹查询时改变了格式

HashUtils 已正确生成 64 位小写 SHA-256。saveFile 用这个字符串保存 metaIndex；getMeta 却将输入转成大写再查询。这里实际发生的是索引键不一致，并不存在题解旧版所推测的“缺少前导补零”。

参考实现将查询键统一为小写。业务上的指纹语义仍由原始附件字节决定，不需要另造一套算法。

## 图片经过字符转换后损坏

starter 解码得到 byte[] 后，执行 new String(fileBytes, UTF_8)，再通过 FileWriter 保存。任意二进制不保证是合法 UTF-8；转换会替换无法解码的字节，字符写入还受默认编码影响。

普通文本可能碰巧正常，图片中的 PNG、IHDR、IEND 等可见片段也可能仍存在，但这不能证明图片完整。参考实现用 Files.write 直接写原始字节。判题通过原始响应字节的 SHA-256 检查完整性，避免仅检查文本片段的漏判。

## 历史客户端请求中的字符变化

随工程提供的 samples/upload-request.json 是兼容范围内的原始请求。content 的留存值为 QUI Q0Q=；恢复为 QUI+Q0Q= 后，解码得到五个字节 41 42 3e 43 44，即 AB>CD。

参考实现于 Base64 解码前，将历史请求中的空格恢复为加号。标准 JSON 解析本身不会把加号转换为空格；这种变换典型地来自上游表单或错误的 URL 解码。本题模拟的是链路已经处理后的历史输入，不能把它归因于当前 Spring JSON 入口，也不应随意删除所有空白来“容错”。

实际系统应同时调查发生错误转换的上游，兼容入口则应明确支持范围。本题不要求增加新的传输链路。

## 修复后的验证

- 返回的指纹可以直接用于查询和下载，且符合约定的 SHA-256 格式。
- 文本、图片与历史请求样本均可完成上传，下载结果与原始附件逐字节相同。
- 既有不存在文件的响应语义保持不变：元信息查询返回 404 JSON，下载接口返回 HTTP 404。
- starter 与 reference 的差异集中在查询键、字节写入和历史输入兼容三处。
